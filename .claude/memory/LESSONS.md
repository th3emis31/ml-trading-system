- 2026-09-13 [research]: The live model's label (close up in 3 bars) does not match how trades are judged (TP before SL over 24 bars); a model can be ~51% 'accurate' and still lose 60%. Judge models by after-cost trading results on a holdout, never by accuracy.
- 2026-09-13 [research]: A model that looks great on validation folds (PF 1.6-1.7) can collapse on an untouched holdout; always keep a holdout that selection never sees, and prefer simpler models when data is only a few thousand bars.
- 2026-09-13 [mt5]: Never call MetaTrader5.initialize()/copy_rates/shutdown() from a second Python process while app.py holds its MT5 connection - the app process restarted right after such a read-only query. Read broker candles through the app's own connection (an app endpoint) instead.
- 2026-09-13 [research]: Best-of-63 selection on small validation samples (33-65 trades) produced validation PF 2.2-3.5 that collapsed on holdout. Require per-fold consistency (R9) and more trades (lower timeframes via broker data) before trusting any pick.
- 2026-09-13 [research]: This PC has ~7.4 GB RAM shared with app.py, MetaTrader terminals and a browser; a full parallel research queue was stopped by the system for low memory. Run research one symbol per process with a free-RAM guard (>=1.2 GB) and RESEARCH_JOBS=4 threads. src/train.py used to import LSTMTrader at module level, loading TensorFlow (~1 GB committed) into every research process; it is now imported inside train_lstm_model.
- 2026-09-13 [research]: With ~1.2 GB free RAM, random-forest research pieces on 4h+MTF are killed by the memory monitor even at RESEARCH_JOBS=1, while logit/xgb pieces finish. Combine the finished pieces (a subset search is still validation-only selection) and note which pieces are missing, rather than retrying the same run.
- 2026-09-13 [research]: A holdout that falls in one strong regime (gold 2024-26 bull run) makes simple rules look great (breakout PF 1.46-1.56) even though they lost on every earlier fold. Always run the plain rules/baselines on the validation folds too, and only trust a model that is positive in BOTH validation and holdout.
- 2026-09-13 [MT4]: MT4 DID hot-reload a recompiled expert (Experts log: 'uninit reason 2' then 'loaded successfully'/'initialized'). Before telling the user to re-attach an EA, grep MQL4/Logs/2026-09-27.log (UTF-16) for that sequence after the .ex4 compile time.
- 2026-09-13 [research]: The 'killed for low memory' research failures were the background-task memory monitor, not real OOM: the same rf/balanced gold 4h MTF piece finished in 186 s in the foreground. Run research in the foreground; do not ask the user to close programs without per-process numbers. (PowerShell inside bash double quotes loses $_ - use a .ps1 file.)
- 2026-09-13 [app]: app.py runs under C:\Users\th_em\start_trading.bat, a 'goto start' keep-alive loop launched at login by the Startup shortcut SmartEntryProAI.lnk; it relaunches app.py 5 s after it exits. Restart the app by stopping ONLY the python app.py process and letting the loop start it. - 2026-09-13 [doctor]: Health checks must model how the app really gates execution: asset auto_enabled alone cannot trade (app._autonomy_should_execute also needs an active session and autonomy.auto_execute), so flagging it as a warning was a false alarm. Read the gate before classifying a flag.
- 2026-09-13 [jarvis]: JARVIS command handlers contained hard-coded replies claiming trades were executed with invented prices (gold 2510/2580 while price was 4348) and one-click autonomy enablement. - 2026-09-16 [news]: The 18:00 UTC FOMC decision printed an XAUUSD H1 candle (broker bars) of range 110.13 (high 4367.47, low 4257.34; open 4361.62, close 4261.01, -100.6), 7.17x ATR14 of 15.36, and the 19:00 bar ranged another 52 while forming. The old filter only blocked 30 min either side of any High-impact USD event and had no history to test. Treat FOMC/CPI/NFP as tier-1 (no entries 60 min before to 90 min after, alert 60 min before to reduce or flatten), block entries for 3 bars after an H1 range > 3x ATR14, and backtest news rules from data/historical_events.csv instead of assuming the filter works.

- 2026-09-27 [testing]: I reported `tests/test_active_account.py` as HANGING at import. **Wrong.** It passes 13 tests in 4.71 s. `tests/conftest.py` copies `data/` and `models/` — about **4.4 GB** — into a temp sandbox on EVERY pytest invocation and deletes it at session end, so any `pytest` command costs ~170 s of wall clock no matter how few tests it selects. Its own imports take 6 s. Three consequences: pytest's reported duration is TEST time, not wall clock, so `13 passed in 4.71s` really took 175 s; running the suite file-by-file is the worst possible strategy (123 files x 4.4 GB = hours and ~540 GB of disk churn), so always run it as ONE process; and a killed run cannot delete its own sandbox while `_sweep_stale_sandboxes` only reclaims ones older than 6 hours, so killed runs pile up — three kills left **9 sandboxes holding 30.9 GB**. After any interrupted suite, check `%TEMP%\smartentry_tests_*` and remove them.
- 2026-09-27 [background jobs]: When the harness reports a background Bash command "killed because the system is running low on memory", it kills the shell WRAPPER and leaves the child alive. An orphaned `python -m pytest` held 550 MB on a 7.4 GB machine and caused two further jobs to be killed in turn. After any such kill, list processes by command line and end the orphan before retrying — and check it is genuinely the orphan, not `app.py` or the scheduled `src.strategy_lab run`.
- 2026-09-27 [hooks]: `py()` in `scripts/claude-hooks/_common.sh` probed with `command -v python3`, which on Windows matches the Microsoft Store App Execution Alias — a stub that exists on PATH, exits non-zero and prints "Python was not found". Every post-edit syntax check therefore reported a false SYNTAX ERROR and verified nothing. A probe must require the candidate to RUN (`"$c" -c ''`), not merely to exist. This fix has now been lost to a git reset once; check it is present before trusting the hook.


- 2026-09-27 [autostart]: A "refuse to become a second server" guard that only checks for a LISTENING socket is not a guard — app.py needs ~30 s to bind (Keras + yfinance imports), so two launchers 29 s apart both passed it and two servers shared port 5000 for a day → check for a running app.py PROCESS, which exists from second zero, and keep the check failing safe (a token on stdout, never an exit code, so a PowerShell failure starts the app rather than blocking boot).
- 2026-09-27 [autostart]: A liveness probe must ask the cheapest question that answers it. start_everything.ps1 asked GET /api/signals with -TimeoutSec 8 to decide whether the app was up; that endpoint runs RF+LSTM inference for every symbol and measures 5-11 s (once 60 s+ under heavy load), so an 8 s timeout lost exactly when the machine was busiest - at boot - and every loss made the script launch a second app → probe the port with a TCP connect (255 ms) when the question is "does something own the port".
- 2026-09-27 [autostart]: The forward-slash/backslash trap CLAUDE.md warns about was live in start_everything.ps1 - Test-Running compared machine.json's forward-slash paths to Windows ExecutablePath's backslashes with -eq, so it was ALWAYS false: five running terminals all reported not-running, and the needless 45 s sleep fired at every boot → normalise both sides (and compare case-insensitively) before any path equality test.
- 2026-09-27 [evidence]: A log that silently drops concurrent writers cannot be used to count concurrent runs. autostart.log's Add-Content failed under contention and $ErrorActionPreference='SilentlyContinue' hid it, so 4 parallel runs logged 1 - and I wrongly concluded from a single log header that only one copy ran on 26 September → serialise log writes before reasoning about how many times something ran, and never treat "one entry" as "one run" in a log with unsynchronised appends.
- 2026-09-27 [mt5]: MT5Service.status() was `self._connected or self.connect()`, so once the flag was True it never reconnected - the app reported "MT5 connected" for over an hour while symbol_info said XAUUSD was "not found on broker", positions_get returned None and account_info returned null, and the System Doctor believed it because it asks that method → probe liveness (terminal_info + account_info, sub-millisecond local IPC) on every status() call and reconnect when it is dead; a cached connection flag is not a connection.
- 2026-09-27 [mt5]: The MetaTrader terminal updates ITSELF (LiveUpdate) and restarts, which invalidates the app's Python link without anything in the app noticing - the 11581419 terminal did this at 13:30 and came back as build 6230, healthy, 1230 symbols → never assume a broker link outlives the terminal process; treat "the terminal restarted" as a normal event to recover from, not an incident.
- 2026-09-27 [costs]: The SHORT overnight swap was never measured - it was set equal to the long rate with the note "short side assumed equal to long", and it was wrong in SIGN. Read from the broker (MT5 symbol_info): gold swap_short is +34.41 POINTS, a CREDIT of 0.3441 price per night, while the table charged 0.0190% as a cost; bitcoin swap_short is 0.0, so shorts are not financed at all while the table charged 0.0560% a night. Every short backtest was over-charged - on XAUUSD:4h by 0.35-1.32 percentage points, moving one of six variants from -1.93% to +2.46% → never let a cost stay an assumption when the broker will state it; read swap_long/swap_short and swap_mode, and remember mode 1 is POINTS and mode 5 is annual percent.
- 2026-09-27 [sweeps]: direction_sweep overwrote each spec's own `family` with the registry key, so `sweep_reclaim` - whose specs declare family "sweep_reversal" - had no builder under its key, reported "no registered builder", and was silently skipped by every sweep that claimed to test every strategy. The owner's 26 September reclaim rule had therefore NEVER been measured → a grid label is not an engine family; fall back to the family the specs themselves name.
- 2026-09-27 [testing]: Two "bugs" found today were defects in my own audit, not the code: a metric comparison that flagged sharpe because the engine rounds to 3dp and I compared against full precision, and a DTypePromotionError from passing evaluate_family the string 'short' where its signature takes side_wanted as an int ±1 → when a check fails, suspect the check before the system, and read the signature rather than inferring it from the caller's vocabulary.
- 2026-09-28 [test infrastructure]: The bar cache leaks without bound and it is what stops the test suite running. `mtf_data.load_bars` writes a new CSV per cache bucket and never removes the previous one, so `data/research/cache` held **1,186 files / 3,973 MB** - 318 buckets of `btcusd_15m_app` and 324 of `xauusd_15m_app`, of which only the newest is ever read. Keeping one bucket per series would be 20 files / 71 MB, so **3,903 MB is superseded and regenerable**. That dead cache is 91 % of what `tests/conftest.py` copies into a fresh sandbox on EVERY pytest invocation, which is why a 7.4 GB machine with under 1 GB free cannot finish a full run: short runs squeak through, long ones are killed. Same unbounded-leak pattern as the 89 sandboxes / 225 GB incident, one layer down. Before concluding "the suite cannot run here", measure `data/` and check what the conftest is copying.
- 2026-09-28 [diagnosis]: I blamed TensorFlow for the memory kills and split the suite to exclude it; the no-TensorFlow run died too, which disproved it in one step. The cause was the 4.4 GB sandbox copy, not the test contents. A split that still fails is evidence, not bad luck - stop and re-measure rather than splitting further.
- 2026-09-28 [blast radius]: A full-suite pass is not always the right regression check. For STEP 3 only three test files touched the changed modules and nothing outside `engine/` imported them, so the 169-test engine run was a COMPLETE check and the full suite would have added reassurance about unrelated code rather than evidence about the change. Measure which tests can be affected before treating a blocked full run as a blocked verification.
